- [x] 16.2 Return `404` rather than `403` for unauthorized reads of existing objects, and verify the response does not distinguish a forbidden object from a missing one — asserted by comparing status *and* body between a forbidden link and an identifier that never existed, since a difference in either is the disclosure the rule exists to prevent
- [x] 16.3 Create the append-only audit table and revoke `UPDATE` and `DELETE` from the application's database role, and verify the application cannot alter an entry even through a direct query. This exposed that the guarantee was unenforceable as deployed: the application connected as the Postgres **superuser**, which bypasses every permission check, so the revoke was decoration. Postgres now creates a separate unprivileged role for the application while the superuser owns the schema and applies migrations — the same two-identity split ClickHouse already used for reads. Verified by `scripts/verify-audit-immutability.sh`, which first asserts the application is not a superuser, because every check after that is meaningless otherwise
- [x] 16.4 Record audit entries for authentication outcomes, role changes, invitations, tokens, second-factor changes, domain changes, settings changes, link password changes, exports and installation, and verify each event produces one entry with actor, action, target, derived source and time. Every secret is asserted absent from its own entry: the invitation token, the API token, the link password, the settings value, and the submitted password on a failed sign-in. The source is an HMAC of the address, never the address. The actor's email is copied onto the entry rather than joined, so the record survives the account being deleted — also asserted. Second-factor enrolment has its actions declared but no call site yet; it is wired when phase 17 builds them
- [x] 16.5 Sweep every endpoint against the IDOR checklist in `specs/security/`, and verify each nested and cross-owner access path is covered by a test — 19 cases across links and everything nested under one, users and role grants, domains, invitations, tokens, settings and branding, including that a claimed role in the query string or body changes nothing because the decision reads stored state

## 17. Two-factor authentication

- [x] 17.1 Implement authenticator-app enrolment with confirmation, and verify a wrong confirmation code does not activate the factor. A factor is inert until proved once, so a secret copied wrong cannot lock anybody out of their own instance. The secret is encrypted at rest and asserted absent from the stored row
- [x] 17.2 Enforce the second factor during sign-in so no session is established until it is satisfied, and verify a correct password alone grants nothing — the response is `202` with no session, and an authenticated endpoint still answers `401`. The pending account is held in the session rather than handed to the client, so nothing the browser can edit decides who is about to be signed in, and the challenge expires on its own
- [x] 17.3 Reject replayed one-time codes within their validity window, and verify a second submission of an accepted code is refused. The accepted time step is recorded rather than the code, so a replay is refused by arithmetic instead of by remembering every code ever seen. This is strict enough that the tests had to travel forward in time to sign in after enrolling — which is the rule working, not a test artefact
- [x] 17.4 Issue, hash and consume single-use recovery codes, and verify a used code cannot be reused and the remaining count is reported. Issued once on the first factor rather than per factor, stored as hashes only, and asserted absent in plaintext from the table. Removing the last factor deletes them, because a recovery code exists to get past a second factor and there is none left to get past
- [x] 17.5 Implement WebAuthn passkey registration and authentication, and verify a registered credential authenticates and is listed with its creation date. Verified in a browser against Chrome's virtual authenticator, which performs the real ceremony: this is signature verification against a real key, and there is no honest way to assert it at the API boundary. The relying party is the instance's own host from configuration and never from the request — that binding is what stops a credential being replayed from elsewhere. Attestation is deliberately `none`: verifying it would mean carrying a metadata service and deciding which authenticator vendors an operator may own. The suite uses its own account, because enrolling a factor on the shared one sends every other browser test to a challenge screen
- [x] 17.6 Implement the instance-wide second-factor requirement, and verify an account without one is confined to enrolment and cannot remove its only factor while the requirement is active. Enrolment, sign-out and reading your own account sit above the requirement rather than behind it — the first attempt put them behind it, which made the requirement a locked door with the key on the inside, and the test caught it

## 18. Supply chain and release gates

- [x] 18.1 Add dependency advisory scanning for both applications to CI, failing on high or critical, and verify it fails against a deliberately vulnerable pinned dependency. Low and medium are reported but do not fail: a gate that fires on everything gets switched off, and the ones that matter go with it. Verified against a throwaway project pinning `guzzlehttp/guzzle` 6.5.0 — which also showed Composer refusing to install an advisory-affected package at all, so the audit had to be reached with `block-insecure` disabled
- [x] 18.2 Add repository secret scanning to CI, and verify it fails on a planted credential-shaped string. Scans history *and* the working tree: the history scan cannot see a file that has not been committed, which is exactly when catching it is still cheap — the first version missed a planted secret for that reason. Findings are redacted in output, because a build log is often less protected than the repository. The one existing finding is allowlisted by fingerprint rather than by file, so a genuine leak in the same file still fails
- [x] 18.3 Add built-image vulnerability scanning, failing on high or critical, and verify it reports against a known-vulnerable base. It found real fixable vulnerabilities on the first run, which is what a scan is for. The web image was fixed rather than excused: npm and corepack are build tools and the runtime runs a standalone bundle, so removing them took their advisories out of the shipped image entirely. What remains is documented one entry at a time — kernel headers, which describe a kernel a container does not run, excluded by package in the scanner; and Go modules vendored into the FrankenPHP binary, excluded with an expiry because no published image carries the fix yet
- [x] 18.4 Add a check that every base image is digest-pinned, and verify it fails on a tag-only reference — demonstrated by removing a digest and watching it name the file and line, then restoring it
- [x] 18.5 Add automated dependency update proposals covering Composer, npm, Docker base images and the workflow's own actions. Minor and patch updates are grouped: a stream of single-package proposals gets closed unread, which is the same as not having them, while security updates stay ungrouped because those are meant to interrupt. Base images are included because a digest pin is what stops anything else noticing a rebuild. **Not verified end to end**: a proposal only opens once the configuration is on the default branch, and this work is on a feature branch — the first run after merge is where that is observed
